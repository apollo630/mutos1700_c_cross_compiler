## 📂 Directory Structure & Context

### Core Toolchain for the MUTOS1700 Cross C Compiler (`/src`)
* `/src/h/`: Core header files (`.h`). Contains shared definitions and system structures:
  `mutos_aout.h` (the `a.out` format) and `mutos_root.h` (the lookup of an absolute MUTOS
  path under the MUTOS root, `$MUTOS_ROOT` or the compiled-in default - for every tool).
* `/src/mutos_ld/`: Source code for the Mutos Linker - since 2026-10-22 a port of the
  original MUTOS 1700 `ld` read from its binary (v7's `ld.c` with the MUTOS deltas),
  running on an image of its data segment (`ld.h`), with `-r`/`-d` as a documented
  extension; `src/mutos_ld/README.md` has the original's behaviour, its deltas from v7,
  the extension and what the port refuses.
* `/src/mutos_as/`: Source code for the Mutos Assembler.
* `/src/mutos_cpp/`: Source code for the Mutos C Preprocessor - since 2026-10-22 a port of
  the original MUTOS 1700 `cpp` read from its binary, running on an image of its data
  segment (`cpp.h`); `src/mutos_cpp/README.md` has the original's behaviour, its deltas
  from v7 and what the port refuses.
* `/src/mutos_cc/`: Source code for the Mutos C Compiler. Contains the driver `mutos_cc` -
  since 2026-10-24 a port of the original MUTOS 1700 `cc` read from its binary
  (`src/mutos_cc/ccport/`, v7's `cc.c` with the MUTOS deltas), running on an image of
  its 64K segment, its passes found through the MUTOS root -, `mutos_c0` (front end -
  since 2026-10-18 a port of the original MUTOS 1700 `c0` read from its binary,
  `src/mutos_cc/c0port/`, see `docs/C0_PORT_PLAN.md`) and `mutos_c1` (back end - since
  2026-10-13 a port of the original `c1`, `src/mutos_cc/c1port/`, see
  `docs/C1_PORT_PLAN.md`), both verified byte-exact end-to-end against every golden of
  `tests/mutos_cc/` (62/62 of the construct corpus, the nine `11_kernel` files, the
  `fltprobe` probes) and against the emulated originals - see `src/mutos_cc/README.md`
  for the `temp1`/`temp2` wire format and the two ports. Also contains `dump_temp.py`, a
  standalone human-readable decoder for any `.1`/`.2` file (generated or golden) — see
  `src/mutos_cc/README.md`'s "Tooling" section, and Workflow Guideline 8 below for the
  rule that keeps it in sync with the wire format. The optimizer `mutos_c2` is since
  2026-10-25 a port of the original MUTOS 1700 `c2` read from its binary
  (`src/mutos_cc/c2port/`, v7's `c2` rewritten for the 8086 with new passes), running on
  an image of its data segment, libc.a's stdio included; `src/mutos_cc/README.md` has
  the driver's and `c2`'s behaviour, their deltas from v7 and what the ports refuse.
* `/src/mutos_ar/` and `/src/mutos_ranlib/` (since 2026-10-26): Source code for the Mutos
  Archiver and the Mutos Archive Indexer - ports of the original MUTOS 1700 `ar` and
  `ranlib` read from their binaries (v7's `ar.c` and `ranlib.c` with the MUTOS
  representation: 26-byte archive headers, longs high word first, signed chars, libc.a's
  `perror`/`mktemp`/`ctime` and stdio slots); `mutos_ranlib` runs `bin/ar` of the MUTOS
  root as the original runs `ar` through the shell. Their READMEs have the behaviour,
  the deltas from v7 and what the ports refuse.
* `/mutos_root/` (generated by `make` through `scripts/mutos_root.sh`, removed by
  `make clean`, ignored by git): the MUTOS root - a directory that mirrors the MUTOS
  file system (`lib/crt0.o`, `lib/libc.a` at its `__.SYMDEF` time, the passes as
  symbolic links into `src/` - `lib/c0` .., `bin/as`, `bin/ld`, `bin/cc`, `bin/ar`,
  `bin/ranlib` -, `usr/lib/`, `usr/include/` - the original headers, copied
  from `/mutos/mutos_include/usr/include/` (since 2026-10-25) -, `tmp/`); the tools look up every
  absolute MUTOS path under `$MUTOS_ROOT`, by default this directory
  (`docs/TOOLCHAIN_PLAN.md`, decisions 2 and 3; `src/h/mutos_root.h`).

### 🧪 Test Suites & Golden Masters (`/tests`)
* `/tests/mutos1700_crt0/`: MUTOS1700 C runtime startup code (crt0), includes `crt0.o.base64.txt`.
* `/tests/mutos1700_libc/`: MUTOS1700 libc.a, including all `*.o.base64.txt` object files and `libc.a.base64.txt`.
* `/tests/mutos_as/kernel_nonopt/`: Golden Master test cases for the assembler (non-optimized builds), including `*.golden_base64.txt`. Also has `Makefile.mutos` (`noL`/`L` targets), written for the real-hardware `-L` experiment described below — see that entry for the outcome.
* `/tests/mutos_as/kernel_opt/`: Golden Master test cases for the assembler (optimized builds, `cc -O` - the original `c2`'s output - plus hand-written kernel assembler such as `mch.s`), including `*.golden_base64.txt`. Also has `Makefile.mutos` (`noL`/`L` targets), same purpose.
* `/tests/mutos_as/README.md` + `/tests/mutos_as/Makefile`: the real-hardware "-L" experiment (see `kernel_opt`/`kernel_nonopt` above and Rule 3's "Known, deliberate exception") — **concluded 2026-09-28**: the real `as` does not implement `-L` at all (`Unknown option L ignored`), so no `.oL` goldens were generated. See `STATUS.md`'s open item 6.
* `/tests/mutos_as/float_coverage/`: real-hardware goldens from eight hand-written `.float`/`.double` sources, which pinned down the real assembler's conversion (v7 `atof()` on the 56-bit double, `.float` = its high half, truncated, `libc.a`'s inexact product, a zero keeping what `fac` held, `ldexp`'s wrapped exponent byte - see `src/mutos_as/fltconst.h`). All eight are byte-identical and part of `make test`, as is `fltmodel.py`, an independent Python model of the conversion; `libcatof.py` is a second oracle: `libc.a`'s own `atof` under an 8086 emulator (`make check-libcatof`). See that directory's `README.md` and `STATUS.md`'s open item 7.

* `/tests/mutos_as/libc_recon/`: real `libc.a` objects as assembler goldens, with
  sources **reconstructed** from their disassembly (`ldexp.s` → the real `ldexp.o`,

## 🎯 Project Background & Goal
The objective is to develop a historically accurate Cross-Compiler Toolchain under modern Linux (x86_64) that generates executable binaries for the **MUTOS 1700** operating system.
* **Target System**: MUTOS 1700 ran on the East German Robotron A7100 and A7150 office computers.
* **Compatibility**: Binary and architecture compatible with **Version 7 Unix (V7)**, but running on an x86 16-bit architecture (Intel 8086 / NEC V30 Real Mode).
* **Codebase**: Built upon the original Unix V7 source codes by Dennis Ritchie (`cc`, `as`, `ld`) and, since the ports of `c1` and `c0`, upon the original MUTOS 1700 binaries themselves (`mutos/mutos_bin/`), read and re-enacted with the V7 sources as the scaffold.

## 🛠️ Development & Non-Negotiable Rules

### 📋 Strict Core Requirements
1. **K&R Compatibility**: The C compiler frontend/backend must be 100% K&R compatible.
2. **Binary Format**: The object file and executable format must use the original MUTOS 1700 `a.out` layout.
3. **CLI Interface**: `mutos_cc`, `mutos_as`, `mutos_cpp`, and `mutos_ld` - and every port of Milestone 6 - must support identical command-line arguments and switches as their Unix V7 counterparts - in practice as the original MUTOS 1700 binaries, which the ports reproduce (decided 2026-10-20). Where the originals look for files by absolute path, the tools look under `$MUTOS_ROOT` instead (`docs/TOOLCHAIN_PLAN.md`, decision 2); that adds no option.
   * **Known, deliberate exception**: `mutos_as` does **not** implement `as.1`'s `-L`
     switch (control over whether compiler-internal `L`-prefixed labels appear in the
     written symbol table). Every real hardware-linked golden `.o` this project
     validates against includes those labels unconditionally, with no flag involved in
     how they were produced — implementing `-L`'s documented default (excluded) broke
     byte-for-byte golden parity. Matching the golden files takes priority over literal
     switch-for-switch parity with `as.1` here; `-o`/`-W` and everything else are
     unaffected. Do not "fix" this without re-breaking golden parity — see
     `src/mutos_as/assemble.c`'s `-L` comment and `STATUS.md`.
     **Real-hardware finding (2026-09-28), settles one part of the open question**:
     the real MUTOS 1700 `as` binary does not implement `-L` at all —
     `as -L -o v30ide.oL v30ide.s` prints `Unknown option L ignored` and proceeds —
     despite `docs/MUTOS1700_Assembler_as.pdf` sect. 3.1 documenting it (a
     manual/binary mismatch this project cannot resolve). This rules out "the
     kernel build invoked `as -L`" as the explanation for why none of `libc.a`'s
     167 objects (compiled C included) has an `L`-number symbol while every kernel
     golden does — the flag is a no-op on this hardware either way, so no
     per-invocation switch can produce that difference. The underlying
     kernel-vs-libc discrepancy is still open; see `STATUS.md`'s open item 6 for
     the new source-level angle (whether `L`-labels come from the compiler's C
     sources, not the assembler's symbol-table policy).
     **Found 2026-10-20 (emulated original)**: the binary does not implement the
     manual's `-W`, `-D` and `-T` either, but has `-e`, `-g`, `-C` and `-l`; the
     original `cc` always passes `-gC`, which `mutos_as` accepted and ignored from
     2026-10-20 (`docs/TOOLCHAIN_PLAN.md`, decision 9).
     **Measured and done 2026-10-25 (step 5)**: the original's `-C` leaves every
     defined, non-global symbol that starts with a capital `L` out of the symbol table
     (the compiler's `L<number>` labels), and `mutos_as -C` does the same now - which
     is what `mutos_cc` has been passing all along; `-g` has no effect in the original
     either. `-e` (externals only) and `-l` (a listing `x.L`) are **not**
     implemented in `mutos_as` - measured differences, see `STATUS.md`. The 80186/V30
     opcodes - an extension the original lacks - are behind the switch `-1` now
     (without it `mutos_as` refuses them, as the original does).
   * **Ended 2026-10-22 - `mutos_cpp`'s `# N "file"` lines**: until then `mutos_cpp`
     (a re-implementation) never wrote them, regardless of `-P`, since every real
     `.i` golden was made with `-P`. The original `cc` runs `cpp` *without* `-P` for
     every compile, and the original `c0` takes its messages' file name and line
     number from those lines (found 2026-10-20); `mutos_cpp` is now a port of the
     original `cpp` (`docs/TOOLCHAIN_PLAN.md`, step 1) and writes them as it does.
   * **`-P` and `-S` (settled 2026-10-20)**: real `cc.c`'s `-P` makes `cc` exit right
     after `cpp` (`if (pflag) { cflag++; continue; }`), before `-S`'s `sflag` is ever
     reached, so `cc -P -S foo.c` produces only `foo.i` — found the hard way generating
     `tests/mutos_cc/`'s golden corpus (`docs/devlog/m4_foundations.md`, "MUTOS 1700
     host-tooling findings"). The original MUTOS `cc` does the same, in either order
     (traced under the emulator); `mutos_cc`, a port of it, reproduces it.
   * **`mutos_ld`'s `-r` and `-d`** (decided 2026-10-20): the original `ld` refuses
     both (`ld: -r and -d flags not supported`); `mutos_ld` keeps them as a documented
     extension - since its port (2026-10-22) v7's meaning with MUTOS's object
     convention, marked "EXTENSION" in `src/mutos_ld/ld.c`, checked by
     `tests/mutos_ld/check_rflag.py`; without them the port is the original.
4. **Headers & Syscalls**: Provide full support for original MUTOS 1700 header files and system calls (mapping x86 software interrupts/traps instead of PDP-11 traps). The original headers are in `/mutos/mutos_include/` since 2026-10-25; `make` copies its `usr/include/` into the MUTOS root (`docs/TOOLCHAIN_PLAN.md`, decision 3).
5. **PDP-11 Middle-Endian — scope**: Historic V7/PDP-11 `long` fields use PDP-11
   Middle-Endian byte order (`1 0 3 2`, i.e. the high-order 16-bit word first, each word
   itself little-endian). This does **not** apply blanket-wide across the toolchain —
   confirmed and implemented scope is:
   * **`ar` archive format** (`atime`/`asize`/`cloc` in `src/h/mutos_aout.h`): carried
     over unmodified from V7, **DOES** use PDP-11 middle-endian. Implemented in
     `mutos_get_u32_pdp11()`/`mutos_put_u32_pdp11()`.
   * **MUTOS `a.out` object/executable header and symbol table**: entirely 16-bit
     based — there is **no `long` field anywhere in it at all** — so PDP-11
     middle-endian is simply not applicable there; every multi-byte field is plain
     little-endian (see `mutos_aout.h`'s own top-of-file comment). Do not apply
     middle-endian encoding to the `a.out` header — doing so breaks byte-for-byte
     golden parity.
   * **`long` variables inside C code compiled by `mutos_cc`**: this is where the rule
     will actually matter for K&R `long`-arithmetic correctness — confirmed (not just
     theorized) via real hardware-linked `.o` disassembly, see `docs/MUTOS_C_ABI.md`
     sect. 1.6 — and **implemented** for `long` locals, constants, parameters,
     return values and `+`/`-`/`*`/`/`/`%` (all of `tests/mutos_cc/02_long`, byte-exact),
     and since `mutos_c1` and `mutos_c0` are ports of the originals, wherever the
     original compiler uses it.
   * **`float`/`double` values do NOT follow it either**: MUTOS 1700's floating
     format keeps the whole value little-endian, the excess-128 exponent in the
     HIGHEST byte and the sign in the top bit of the byte below it (v7's
     "0.1xxx" mantissa otherwise) - read off real `libc.a` data bytes
     (`atof.o`'s `2**56` is `00 00 00 b9`, `ecvt.o`'s `10.0` is `00 00 20 84`),
     not PDP-11 word order. See `docs/devlog/m4_handwritten.md`'s `08_float` section.
   * *Example (for the `ar` archive and compiled `long` values only)* — storing
     `0x0A0B0C0D`:
     ```text
     byte offset        8-bit value     16-bit little-endian value
        0               0Bh             0A0Bh
        1               0Ah
        2               0Dh             0C0Dh
        3               0Ch
     ```
6. **Identifier length limits**: this toolchain's real significant-character limits
   are **8 for internal identifiers, 7 for external (global-linkage) identifiers** —
   confirmed from two independent sources and load-bearing for `mutos_c0`/`mutos_c1`,
   not just a test-corpus style rule:
   * **Internal = 8**: `v7/cc/c0.h`/`c1.h` define `NCPS 8` — the compiler's own
     front-end symbol table (`struct hshtab`) has an 8-byte name field. Applies to
     anything that never leaves the compiler's own symbol table: locals, parameters,
     struct/union members, `typedef` names, `enum` constants, labels. Two internal
     names agreeing on their first 8 characters are the same symbol to `c0`/`c1`.
   * **External = 7**: `man/mutos_aout.h.5`'s `mutos_sym_t.name[8]` - the original
     `a.out.h`'s `n_name[8]` (`/mutos/mutos_include/usr/include/`) - shows the
     **object-file** symbol table entry is also 8 bytes — but `v7/cc/c04.c`'s
     `outcode()` (confirmed in `c02.c`'s `EXTERN`/`STATIC`/`CSPACE` handling too)
     unconditionally prepends a leading `_` to any name written there, consuming one
     of those 8 bytes. Applies to any function name and any file-scope variable,
     `static` or not. `mutos_c1` must reproduce this truncation-after-underscore
     behavior exactly (not just avoid overlong names in its own test data) to stay
     byte-for-byte compatible with real MUTOS 1700 object output.
   * See `tests/mutos_cc/README.md` for the derivation in full and two identifiers
     the test corpus itself had to be renamed for after violating the 7-char limit.

### 📋 Workflow Guidelines
1. **Context Alignment**: Before modifying code in `/src/mutos_<tool>/`, always check the corresponding test suite in `/tests/mutos_<tool>/` to understand the expected behavior and existing edge cases.
2. **Golden Master Integrity**: Do not alter files in `/tests/.../kernel_opt/` or `kernel_nonopt/` unless explicitly instructed. These serve as our regression baseline.
   * The same holds for everything under `/mutos/` - the original binaries, headers and
     manual pages: never regenerated, re-encoded, reformatted or altered (see its
     `README.md`).
   * **Caution — `.o` is ambiguous in this repo**: every `*.o.golden` under `tests/mutos_as/` is precious real hardware-linked **reference data**, not a regenerable build byproduct, even though it shares the `.o` extension with actual build artifacts (e.g. `src/mutos_as/*.o`). A blanket `find . -name "*.o" -delete` or `make clean`-style cleanup run from the repo root will destroy those. `tests/mutos1700_libc/*.o.base64.txt`, `tests/mutos1700_libc/libc.a.base64.txt`, and `tests/mutos1700_crt0/crt0.o.base64.txt` are the same kind of precious real hardware-linked reference data — stored as base64 *text* (the raw `.o`/`.a` binaries were deleted 2026-09-27) specifically so a `.o`-glob cleanup can't catch them by accident, but they must never be regenerated, re-encoded, or otherwise altered either. Always scope any build-artifact cleanup to the specific `src/mutos_<tool>/` build directory being cleaned, never to `/tests/`.
     Extend the same care to `tests/mutos_as/v30_speculative/`'s `*.o.crosschecked` files
     (if/when present) — do not delete them in a cleanup sweep either, but also never
     treat them as equivalent to a real `*.o.golden`: they are cross-checked against
     third-party tooling only, not hardware-confirmed (see that directory's own
     `README.md`).
3. **Reference Material**: Use the `/v7/` directory strictly as historical reference. Do not mix V7 logic directly into `mutos` unless explicitly migrating or fixing compatibility bugs.
4. **Header Files**: When changing structs or definitions in `/src/h/`, verify the impacts across `as`, `cc`, and `ld` simultaneously.
5. **Build Requirement**: Create one top Level Makefile to build all 4 components (`mutos_ld`, `mutos_as`, `mutos_cpp`, `mutos_cc`). **Done** — see the repo-root `Makefile` (`make`/`make test` — see `STATUS.md`'s "Top-level build"). Every new tool joins it, and so does the MUTOS root `mutos_root/` (`docs/TOOLCHAIN_PLAN.md`, step 0): built by `make`, removed by `make clean` - which never touches `tests/` or `mutos/` (Guideline 2).
6. **STATUS.md Sync (mandatory)**: `STATUS.md` must be kept in sync with reality at all
   times — treat it as part of the change, not optional follow-up documentation. This
   means:
   * Any change to a tool (bug fix, new opcode/feature, CLI change, regression
     discovered, etc.) is only "done" once `STATUS.md` reflects it —
     including rebuilding and diffing against the real golden files first (per this
     project's core verification rule) so `STATUS.md` never states an unverified claim
     as fact.
   * Every tool and milestone - those to come too (`mutos_make`, `mutos_ar`,
     `mutos_ranlib` and the other ports of Milestone 6) - gets its own status section in
     `STATUS.md` as soon as work on it starts, each claim dated ("verified 2026-10-20") or marked as
     carried from an earlier session without being re-run.
   * If a session cannot re-verify a previously-documented claim (e.g. missing golden
     files, as currently the case for `mutos_ld` — see `STATUS.md`), that must be
     stated explicitly in `STATUS.md` rather than silently repeating the old claim.
   * This applies regardless of who or what makes the change — human contributor or AI
     assistant.
   * **`DEVLOG.md` companion**: dense technical detail that doesn't belong in
     `STATUS.md`'s current-state summary (CPU/encoding facts, full bug narratives,
     debugging methodology) belongs in the development log instead - the part under
     `docs/devlog/` it concerns, listed in the index `docs/DEVLOG.md` — added there as
     it's discovered, not just held in conversation memory. A session record that has
     stopped describing the current state moves from `STATUS.md` to `docs/history/`,
     unchanged, rather than being deleted.
   * **Automated backstop**: `make check-docs` (`scripts/check_docs.py`) mechanically
     catches the part of this that's easy to miss by hand — a number restated in more
     than one file that fell out of sync, a stale/renamed filename still quoted
     somewhere, a broken internal link, or a "Last updated" stamp that doesn't match
     the file's actual last commit (for a file with uncommitted changes: today's date,
     the date the pending commit will carry). It runs in CI on every push/PR touching a `.md`
     file (`.github/workflows/docs-consistency.yml`), and — after a one-time
     `make install-hooks` per clone — automatically before every local commit too
     (`.githooks/pre-commit`, blocks the commit on failure; bypass with
     `git commit --no-verify` if genuinely needed). It is a mechanical backstop, not a
     substitute for the sync discipline above — it only catches drift shaped like its
     existing checks, not a claim that's internally self-consistent but wrong.
7. **Download Delivery Format (mandatory)**: When providing repository file updates,
   default to a **git patch** (a plain `git diff`-format file, applied with `git apply
   patch.file` or `patch -p1 < patch.file` from the repo root), not a zip. Generate it
   from a local clone synced to the person's actual current `HEAD` (fetch/merge
   first — don't assume the sandbox's clone is still current) and verify with
   `git apply --check` (ideally against a fresh clone) before handing it over, so it's
   known to apply cleanly rather than just plausible-looking. State explicitly which
   files the patch touches and why (new vs. modified). This replaced an earlier
   zip-of-changed-files default after a real failure mode: with a zip, new (untracked)
   files are easy for the person to miss when copying by hand — that's exactly how
   `tests/mutos_cc/`'s 11 per-category `Makefile.mutos` files went missing from a
   commit even though everything else in that same delivery was copied correctly. A
   patch applies (or cleanly fails) as one atomic unit, so partial-copy mistakes like
   that can't happen silently. Fall back to a zip only when a patch genuinely isn't
   the right tool — e.g. the person explicitly asks for a zip, or the delivery is
   brand-new binary content that isn't already routed through this project's
   base64-text convention (see the `.o`/`.a` golden files above) and so has nothing
   meaningful to diff.
8. **`dump_temp.py` sync (mandatory)**: `src/mutos_cc/dump_temp.py` (a standalone
   human-readable decoder for any `temp1`/`temp2` — i.e. `.1`/`.2` — file, generated or
   golden) decodes each opcode's argument list from a hardcoded table (`OPCODES`),
   transcribed directly from the `outcode()` call sites of `mutos_c0` - the port of
   the real `c0`, `src/mutos_cc/c0port/`, whose call sites are the original's —
   it does not infer shapes from the byte stream itself. This table goes stale
   silently otherwise, so: any change that adds a new opcode `mutos_c0` emits, changes
   an existing opcode's argument count/order, or adds a new `TY_*`/`SC_*` constant
   (`decode_type()`/`decode_sc()`/`SC_NAMES` in the same file) must update
   `dump_temp.py` in the same change — not as separate follow-up work, the same
   standard Workflow Guideline 6 holds `STATUS.md` to. Verify the update the same way
   `dump_temp.py` was originally verified: re-run it against every affected
   `*.1.golden`/`*.2.golden` (`tests/mutos_cc/**/*.1.golden` covers the full corpus)
   and confirm no new opcode stops the dump with a "no confirmed argument shape"
   message that should now be decodable. Since `mutos_c0` is the port it has an entry
   for every opcode the original `c0` can write; an opcode without one stops the
   dump cleanly, per its own header comment, rather than guessing.
9. **Bugs of the MUTOS originals (mandatory)**: every bug found in an original MUTOS
   1700 tool - `c0`, `c1`, `as`, `ld`, `cpp`, `cc`, `c2`, `libc.a`, and `make`, `ar`,
   `ranlib`, `nm`, `size`, `strip`, `tsort`, `ed`, `em` as they are read -
   goes into `docs/MUTOS_ORIGINAL_BUGS.md` in the same change that finds it, so that
   it can be fixed later: an ID, the symptom with a minimal trigger where one is
   known, the mechanism (text or data offset in the binary), the evidence (golden,
   emulator run, or code reading only), what this project's tool does with it
   (reproduces it, refuses there, or models it), and a fix idea. The project's tools
   stay faithful to the original - bugs included - until a fix is decided; the list
   is where such a fix starts. A bug found by a test (`fuzz_c.py`'s "as the real
   compiler" programs, a refusal of `mutos_c1`, a real-hardware run) is not done until
   its entry is there.
10. **Man pages at the end (decided 2026-10-20)**: the man pages in `man/` are written
    when the project is finished; the existing ones stay as they are until then, also
    where they no longer describe the tools. Requirements for them: **English**; **no
    development details** (no session history, no plans, no references to this
    repository's development documents or test files); **references to the other
    tools** (`SEE ALSO`, and wherever one tool hands work to another); **consistent
    wording and structure** across all pages.

## 🗺️ Strategic Roadmap & Current Focus
The project follows a strict **Bottom-Up** strategy. See **[`STATUS.md`](./STATUS.md)**
for verified current implementation status per milestone — the summaries below describe
scope and intent, not a snapshot of what's done. The decisions of 2026-10-20 and
2026-10-25 and the order of the work ahead are in
**[`docs/TOOLCHAIN_PLAN.md`](./docs/TOOLCHAIN_PLAN.md)**.

**Method for every remaining tool (decided 2026-10-20)**: a port of the original
MUTOS 1700 binary, as `c0` and `c1` were ported - the binary is the specification, the
v7 source the scaffold where there is one, and the original running under the emulator
(`tests/realbin/`) the oracle on every golden and on random input.

**The MUTOS root (decided 2026-10-20)**: every absolute path an original tool has
compiled in (`/lib/crt0.o`, `/lib/c0`, `-lc` → `/lib/libc.a`, `/usr/include`) is
looked up under `$MUTOS_ROOT` - an environment variable, by default the build tree's
`mutos_root/` (compiled in at build time). No new command-line option; the host's own
`/lib` and `/usr/lib` are never used.

### Milestone 1: The Cross-Linker (`mutos_ld`)
* **A port of the original `ld` binary since 2026-10-22** (`docs/TOOLCHAIN_PLAN.md`,
  step 2): `-l` under the MUTOS root, the six bytes of `eb fe` after the text, the
  byte-shifted relocation words (`bytrel()`), the original's bugs
  (`docs/MUTOS_ORIGINAL_BUGS.md`, LD-01 ..); `-r`/`-d` (which the original refuses)
  kept as a documented extension. Checked against the emulated original (its own
  goldens are missing) on every compiled golden with a matrix of options, on
  hand-written cases and by differential fuzzing - see `STATUS.md` and
  `src/mutos_ld/README.md`. Until then a port of v7's `ld.c` with the MUTOS deltas known
  then (the git history).

### Milestone 2: The Cross-Assembler (`mutos_as`) [CURRENT FOCUS]
* Parsing MUTOS 1700 assembler syntax and emitting 8086 opcodes into MUTOS-compatible
  object files (`.o`): **provisionally complete** — see `STATUS.md`.
* NEC V30/80186 instruction-set support: a set of 80186/V30 opcodes (PUSHA/POPA, PUSH
  imm, INSB/INSW/OUTSB/OUTSW, ENTER/LEAVE/BOUND, IMUL-immediate forms,
  shift/rotate-with-immediate-count) is implemented; the original `as` has none of
  them. **Done 2026-10-25** (decided 2026-10-20): they are behind the switch `-1`
  (`docs/TOOLCHAIN_PLAN.md`, section 4; `tests/mutos_as/check_switches.sh`).
* `-g`/`-C` (the original `cc` passes `-gC`): `-g` is ignored, as in the original;
  `-C` drops the defined, non-global `L` symbols, as measured on the original
  (2026-10-25).
* **Step 5 of `docs/TOOLCHAIN_PLAN.md` done 2026-10-25**: a differential fuzzer
  (`tests/realbin/asfuzz.py`) and a comparator (`tests/realbin/ascmp.py`) against the
  emulated original `as`. The compiler's own output is assembled byte-identically; the
  remaining differences (an assembler for hand-written code only) are listed in
  `STATUS.md`. **Open: the decision whether to port `as`** - the user's, with the
  measurements and a recommendation in `STATUS.md`. No 8087 support needed.

### Milestone 3: The C Preprocessor (`mutos_cpp`)
* **A port of the original `cpp` binary since 2026-10-22** (`cpp.c 1.6 12/12/86`, with
  its symbol table; `docs/TOOLCHAIN_PLAN.md`, step 1): the `# N "file"` lines without
  `-P`, `/usr/include` under the MUTOS root, the original's behaviour in every case the
  re-implementation simplified, its bugs (`docs/MUTOS_ORIGINAL_BUGS.md`, CPP-01 ..).
  Checked against the emulated original on every `.i` golden's source and by
  differential fuzzing - see `STATUS.md` and `src/mutos_cpp/README.md`.

### Milestone 4: The C-Compiler (`mutos_cc`, `mutos_c0`, `mutos_c1`)
* **`c0`/`c1` process split: confirmed, not just inherited.** Deliberately kept as
  two separate executables (matching the "Target Executables" list above) after
  reading `v7/cc`'s actual `temp1`/`temp2` format: it is not a raw memory/pointer
  dump but a small, fully-specified tagged byte stream (`outcode()`/`getree()` in
  `v7/cc/c04.c`/`c11.c`), which makes the split's testability benefit real and
  cheap rather than an artifact of the PDP-11's 64K limit. `mutos_c0` should keep
  that stream format close to the original and add an optional human-readable
  dump mode, so its front-end output (parsing, typing, tree shape) can be verified
  against hand-written expected IR before any x86 code generator exists (done as the
  separate decoder `src/mutos_cc/dump_temp.py`). Full rationale in
  `docs/devlog/m4_foundations.md`.
* **`mutos_c1` and `mutos_c0` are ports of the original `c1` (2026-10-13) and `c0`
  (2026-10-18)** - `docs/C1_PORT_PLAN.md`, `docs/C0_PORT_PLAN.md`: every golden of
  `tests/mutos_cc` (the 62-file corpus, `11_kernel`, `fltprobe`) reproduced at every
  stage, no difference against the emulated originals on random programs. The road
  there - the hand-written compiler, corpus category by category and the `fltprobe`
  rounds - is in `docs/devlog/` and `docs/history/`.
* **`mutos_cc` is a port of the original `cc` (2026-10-24)** - not of `v7/cc/cc.c`,
  which it differs from (`-a`, `-K`, `-f`, the new `-o`, `as -gC`; its bugs CC-01 ..
  in `docs/MUTOS_ORIGINAL_BUGS.md`). It finds its passes as `$MUTOS_ROOT/lib/c0` etc.
  (symbolic links in the root) and passes `$MUTOS_ROOT/lib/crt0.o` and `-lc` to `ld`.
  Checked against the original under the emulator, its passes traced
  (`tests/realbin/cccmp.py`, `ccfuzz.py`) - see `STATUS.md` and
  `src/mutos_cc/README.md`. Milestone 4 is complete; `mutos_c2` (Milestone 5)
  followed on 2026-10-25.

### Milestone 5: Optimizer (`c2`) & NEC V30
