# `mutos_c0` as a port of the real `c0` — plan and result

Written 2026-10-14. `STATUS.md`'s "Next up" item 2 asked for `mutos_c0` to
cover `tests/mutos_cc/11_kernel` (it refused eight of the nine real kernel
files) "by the method that made `mutos_c1` exact": a port of the original
binary, checked against the original running under the emulator
(`docs/C1_PORT_PLAN.md`, section 7). This is that port.

**Status (2026-10-18): done - `mutos_c0` is the port** (`src/mutos_cc/c0port/`);
the old from-scratch front end (`c0_lex.c`, `c0_parser.c`, ...) is deleted
(its last version is in the git history, commit `ff1e589`). All nine
kernel files go through `mutos_cpp`, `mutos_c0` and `mutos_c1`
byte-exact. The port was written on 2026-10-14 and checked, finished and
switched on 2026-10-18 (section 5).

## 1. What was ported

The original `c0` (`mutos_bin/c0.golden.base64.txt`, 0411, text 23,168
bytes, stripped) is v7's `c0` compiled for the 8086: `crt0`, then 73
functions in exactly v7's source order (`c00.c` .. `c04.c` - v7's 72 and one
new), then `libc.a` from text `4a1e`. `tests/realbin/c0map.txt` lists every
function with its text offset, its v7 counterpart and what the binary does
differently; `tests/realbin/c0dis.py` disassembles one by name (it is
`c1dis.py` switched to `c0` - `c1dis.use()`).

Every function was read instruction by instruction beside v7's source, the
hashed switches decoded from their jump tables. 60 functions do exactly
what v7's do. The MUTOS deltas are few and local:

| Function | What the binary does differently from v7 |
|---|---|
| `build()` | A relational operator with a constant in -128..127 on one side and a char on the other makes the constant a char (no conversion; text `14c2`). A char operand of `+ - * / %` is converted to int by ITOC (109) first. QUEST and SEQNC keep `p2`'s `subsp`/`strp`. The conversion table is 5x5 words (five type classes) and a code five bits (XX = 16). `dope & LVALUE` where v7 tests ASSGOP (so `++`/`--` take the assignments' rule). No `t==CHAR -> INT`: a result can be CHAR. |
| `convert()` | Two pseudo conversions from `cvntab[]`: 123 (char to floating: ITOC then ITOF) and 122 (floating to char: FTOI then ITOC). |
| `lintyp()` | Five classes: char 0, int/unsigned 1, float/double 2, long 3, else 4. |
| `chkfun()`, `disarray()` | A null tree (an empty argument list) is returned as is. |
| `werror()` | New: `error()`'s text with "WARNING, " - never called. |
| `extdef()` | A static external is `BSS NLABEL name SSPACE size` without v7's `SYMDEF ""`. |
| `cfunc()` | `PROG EVEN RLABEL name`; `regvar` 4 and `STAUTO` -4 (the 8086's DI and SI below BP); `LABEL retlab RETRN <function type>`. |
| `funchead()` | `SETREG regvar` written first, before the parameters. |
| `blockhead()` | No `SETREG`. |
| `goodreg()` | No char register variables; `SETREG regvar` for every register handed out. |
| `getype()` | A parameter list is declared only right after the declarator's name (a static flag at data `40c2`, set by NAME, cleared by `[` and after the list). |
| `decl1()` | Clears that flag first. |

The data: `HSHSIZ` is 500 (v7: 400), `opdope[]` is v7's but EXCLA has
LWORD (so `!d` of a double is "Illegal type of operand") and op 29 is
BINARY; `cvntab[]` has entries 10..15 (ITOC, LTOC 108, CTOL 107, op 29 and
the two pseudo ops); `ctab[]` and the keyword table are v7's ("short" is
INT). `tests/realbin/c0tables.py --tables` prints them from the binary.

## 2. The representation: a memory image

The `c1` port keeps host structures with the original's field offsets.
`c0` lays its structures over one another far more: a `struct hshtab`
built for a cast is used as a tree node with op ETYPE; the tree node
`funcblk` is initialized as a symbol when a structure has too many
initializers; a parameter list is linked through the symbols' `hoffset`
words; a string's tree node points its `subsp` at the global `nchstr`;
and in error paths it reads fields of a null tree - `conexp()` after a
syntax error returns the word at address 8, which `crt0` filled with the
code segment. So the port runs on an image of the original's 64K data
segment (`c0port/c0.h`):

- the binary's initialized data at address 0 (`c0port/c0data.c`,
  generated by `c0tables.py --c` and checked by `make check-realbin`), the
  BSS zero, `crt0`'s two segment words (the emulator's code segment,
  0x1000);
- every global at its original address (`isn` is the word at `000a`,
  `hshtab` 500 entries of 22 bytes at `0b8c`, ...), so that the code reads
  like v7's: `isn++`, `peeksym = o`;
- the heap from the original's break (`418a`) in the original's block
  sizes (a tree node 12 bytes, a symbol 22, a pushed-down symbol 14, ...),
  so that memory a block leaves behind is what the original's leaves;
- pointers as 16-bit addresses, fields as accessors at their byte offsets
  (`OP(p)`, `TYP(p)`, `HCLASS(p)`, ...), words as `int16_t` or `uint16_t`
  so that arithmetic wraps where the original's does;
- the locals whose address the original passes on (`typer`, `mems[]`,
  `dim`, `bstack[]`) in a stack area at the top of the image, and `tree()`'s
  operand stack `cmst[]` one per nesting depth - `cinit()`, `doret()` and
  `dogoto()` keep pushing onto the dead frame's `cmst[]` after `tree()`
  has returned.

The I/O is the host's (the source, temp1, temp2, the messages through a
re-enactment of `libc.a`'s `printf` for `%d %c %s %.8s`); the parts of the
image that are `libc.a`'s stdio state - its FILE structures, the buffers
of stdin, stdout and temp2, its own BSS - are not modelled, and any access
there is refused.

## 3. What makes it checkable

The original runs: `tests/realbin/mutosemu.py` gives all 132 `.1`/`.2`
goldens back. `c0` has no traces, but it needs none - its whole output is
the two temp files, its messages and its exit status, so each run is a
plain comparison (`tests/realbin/c0cmp.py`):

- `c0cmp.py goldens`: every `.i` golden - the 62-file corpus, `fltprobe`,
  `11_kernel` and `tests/mutos_cpp/c`'s five kernel files: 137 inputs;
- `c0fuzz.py`: differential fuzzing with three generators - its own,
  declaration-heavy (storage classes, typedefs, structures, unions, enums,
  bit-fields, constant-expression bounds, initializers of every kind, K&R
  parameters, nested blocks, labels, switches, the old `=+` operators,
  `\/` and `/\`, casts, `sizeof`, string and character escapes, comments,
  `# line` lines, SOH markers), `c1fuzz.py`'s and `fuzz_c.py`'s - and
  `--mutate`, which deletes, duplicates, swaps or inserts tokens: c0's
  error paths, its messages and what it still writes after them.

A refusal counts apart: the port must have written a prefix of what the
original wrote - in each temp file and in the messages before its own
(after a refusal in the stdio buffers, only the original's flushed 512-byte
blocks) -, and where the original does not finish, the port must have
refused. `mutosemu.py` got an `eof_limit`: the original `c0` reads past the
end of the file for ever in three places, and each read is a system call
in the emulator - a thousand reads of nothing stop it.

And `mutosemu.py` got the 8086's shifts. Unicorn executes x86 code as an
80386 does, a shift or rotate by CL taking CL's low five bits; the 8086
(and its clone K1810WM86, `docs/MUTOS1700_Assembler_as.pdf`) and the V30
take all of CL (the
V20/V30 manual: "temp <- CL, while temp != 0"; the 80186 masks, see
`docs/DEVLOG.md`'s CPU reference). So `fold()` of `1 << 40` is 0 on the
hardware and was 256 in the emulator. Every shift by CL in a binary's
text that could run with CL >= 32 now gets a hook that does the 8086's
shift (for a register operand; a memory operand with CL >= 32 stops the
run, not modelled), and the port folds as the 8086 does (`c0port/c01.c`,
as `c1port/c1.h`'s `shl16()`/`sar16()` already did). The same holds for
a signed division whose quotient is -32768: the 8086 (AP-186: "whenever
the absolute value of the quotient is greater than 7FFFH") and the V30
fault, the 80186 and the 80386 do not - `fold()` of `-32768 / 1`.
`mutosemu.py` stops the run with a divide error there, and both ports
refuse (`c1port/c1.h`'s `div16()`/`rem16()` too).

## 4. Refused on purpose

Each stops the port with exit status 2 and "c0: ... refused", after
everything before it was written (`c0trap()`):

- **The original's endless loops at end of file** - an identifier, a
  comment or a `#` line that runs into the end of the file: `ctab[-1]` is
  LETTER, EOF (-1) is not EOFC (0), and the `#` line's skip loop tests a
  flag only `symbol()` sets.
- **CPU faults**: `-32768 / -1`, `-32768 / 1` and their `%` folded by
  `fold()` (the 8086's `idiv` faults), an initialized array of
  zero-length elements (`cinit()` divides by 0).
- **Uninitialized stack words**: `decl1()` returns an uninitialized
  `elsize` after "redeclared" (v7 too) - refused inside a structure's,
  union's or enum's list, where it becomes offsets and the size; a member
  list running past `strdec()`'s `mems[NMEMS]` (structholes are not
  counted against "Too many structure members"); and `dogoto()`'s
  `*cp++ = tree()`, which stores through the `cp` of before `tree()` - into
  a dead frame mostly, refused where it is not (a syntax error, a `cp`
  left by `funchead()`, a goto nested five or more statements below the
  last expression).
- **libc.a's stdio state**: an input byte 0210..0247 in a token position
  (`ctab[]` indexed past its end reads stdin's and the others' FILE
  structures), a number longer than 94 characters (it runs over `numbuf`
  into stdout's buffer), any wild pointer into those parts; a write over
  `crt0`'s far pointers; a heap past `c000` or nesting deeper than the
  image's stack area.

What the port keeps: everything else the original does with its own
memory - a `# line` file name longer than `filename[64]` running into
`symbuf` and `hshtab`, a number of 65..94 characters overwriting
`memlist` and `blklev`, a null tree's fields read from `crt0`'s data and
`isn`, `funcsym` null in "undefined; func. %.8s" (bytes from `000d`), an
enum's size taken from the caller's register (`strdec()`'s `elsize` is
never set for an enum: the original's DI, `getkeywords()`'s storage
class).

Every refusal and every kept case is a bug of the original, listed in
`docs/MUTOS_ORIGINAL_BUGS.md` (C0-01 .. C0-12) with a minimal trigger.

## 5. Result

Numbers of the final build, 2026-10-18 (see `STATUS.md`):

- **Goldens** (`c0cmp.py goldens`): all 137 `.i` inputs identical to the
  emulated original - `.1`, `.2`, messages and exit status -, the same
  with an ASan/UBSan build.
- **`make test`**: 121 files byte-exact at all four stages (the 62-file
  corpus, 50 `fltprobe` files, all nine `11_kernel` files - `02_prim` to
  `09_amx` new), `p19_open3` and the ten files with the real `c1`'s
  messages as before; `run_goldens.sh`'s categories 3 (`mutos_c0`
  refused) and 10 (`mutos_c1` from the goldens alone) are empty.
- **Differential fuzzing** (`c0fuzz.py`, the final build and emulator):
  5,800 programs - 2,000 of its own generator, 2,000 of them mutated, 600
  each of `c1fuzz.py`'s and `fuzz_c.py`'s, 600 of `c1fuzz.py`'s mutated -
  5,723 identical, **none different**, 22 refused (each checked against
  the original's prefix: 12 C0-04, 10 C0-06), 55 on which the original
  does not finish (33 C0-02, 22 C0-03), all refused by the port; 1,000
  more through an ASan/UBSan build, no report. Before the emulator's
  division was fixed, 11,800 more, no difference (see `STATUS.md`).
- **Changed after the first runs**: the port's refusal of a constant
  shifted by 32 or more (56 of the first 2,000 programs), which rested on
  the emulator's 80386 shifts and a wrong reading of the V30's - now both
  shift as the 8086 does (section 3), and those programs are identical;
  and `-32768 / 1`, which the 8086 refuses to divide and the emulator
  did not (section 3). The first runs had found no difference otherwise.
