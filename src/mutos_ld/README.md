# mutos_ld - MUTOS 1700 Cross Linker

`mutos_ld` is a port of the original MUTOS 1700 link editor
(`mutos/mutos_bin/ld.golden.base64.txt`): Unix V7's `ld` with the MUTOS
deltas for the 8086. Every function of the binary was read instruction by
instruction beside `v7/ld/ld.c` - the binary is the specification, v7's
source the skeleton - and the port does what the binary does, its bugs
included (`docs/MUTOS_ORIGINAL_BUGS.md`, LD-01 ..), with one documented
extension: `-r` and `-d`, which the original refuses. It replaced, on
2026-10-22, a port of v7's `ld.c` with the MUTOS deltas as they were
known then (the last version is in the git history, commit `36e69a5`);
see `docs/TOOLCHAIN_PLAN.md`, decision 5 and step 2.

`tests/realbin/ldmap.txt` maps every function to its text offset in the
stripped binary and says what each one does differently from v7;
`tests/realbin/lddis.py` disassembles one by name.

## How it is checked

- `tests/realbin/ldcmp.py goldens` (in `make check-realbin`): every
  `.s.golden` of `tests/mutos_cc` (131 - not `p19_open3`, the real
  compiler's invalid output), assembled by `mutos_as`, linked by the port
  and by the original running under the 8086 emulator with twelve command
  lines each - `cc`'s `-X crt0.o x.o -lc`, without `-X`, `-x`, `-s -o`,
  `-i`, `-n`, `-S -O`, the object alone, `-t -u -e` with `libc.a` by name
  and out of date, `libc.a` by name and current, `-D`, the object twice:
  the messages, the exit status and every file left in the directory
  (bytes and mode) the same.
- `tests/realbin/ldcmp.py cases`: hand-written cases - every message,
  `-v`, `-D`, `-e`, `-u`, `-l` names of every length, archives with and
  without a table of contents, bad and short files, the tables' limits
  (1103 symbols, 1000 undefined references, 700 table entries, 256 archive
  entries, the overflows), the byte-shifted relocations.
- `tests/realbin/ldfuzz.py`: differential fuzzing against the emulated
  original - random objects (every relocation kind, the pc-relative and
  byte-shift bits, every kind of symbol), real `libc.a` members, archives
  plain, current and out of date, random options; with `--mutate` damaged
  files for the error paths.
- `tests/mutos_ld/check_rflag.py`: the extension - every program of the
  construct corpus linked through a relocatable object (`-r`, `-r -d`)
  runs under the emulator as the program linked at once does.
- `tests/mutos_root/check_root.py` (in `make test`): a link through the
  MUTOS root uses `libc.a`'s table of contents ("out of date" only for a
  newer copy).

## The memory image

ld keeps everything in fixed arrays of its data segment and runs past
some of them without a check. So the port keeps the original's 64K data
segment as an image (`ld.h`): the binary's initialized data at address 0
(`lddata.c`, generated by `tests/realbin/ldtables.py --c`), every global
at its address (read from the code), 16-bit pointers and ints, chars read
with their sign, longs with their high word first. A `-l` name of 14
characters or more is written over the strings after the library name
(LD-01), a 257th archive entry over `cursym` and `symtab[]` (LD-02), a 17th
`-v` over the page buffers - in the port as in the original. The one
local whose address the original passes on, `getfile()`'s `struct stat`,
only `fstat()` fills, so the stack is not in the image.
What the image does not model is refused with exit status 2 and a message
ending in "refused" (`ldlib.c`, `ldtrap()`):

- libc.a's data and BSS (the FILE structures, printf's state, the stdout
  buffer), crt0's words but for reading: a long `-l` name reaching them;
- an `lseek()` to a negative offset - MUTOS's kernel (v7's `seek()`) takes
  it and fails the read after it, the emulator fails the seek; reached by
  an object of 32K or more of text or data (LD-07) and by damaged archives;
- an input that is a directory (the original reads its entries);
- a printf conversion the port's printf does not have (only from a format
  string a long `-l` name has written over: LD-01).

## Behaviour (the original's)

As v7's `ld`, with these MUTOS deltas (`tests/realbin/ldmap.txt`):

- Objects: a relocation word's bit 15 says the word relocated starts at
  the next byte (8086 operands are not word-aligned) - `bytrel()` adds to
  that word across two of the file's words, the carry into the second;
  bit 0 is pc-relative; bits 4 to 14 index an external symbol. A data or
  BSS symbol's value, and a data or BSS relocation's base, is an offset in
  its own segment. A symbol's type is read and compared as a word - its
  type byte and the spare byte together.
- The text gets six bytes of "jmp $" (`eb fe eb fe eb fe`) at its end,
  counted in its size; `-i` (and `-n`, which sets the same flag: a 0411
  output) then pads it to 64 bytes with zeros and starts the data at 0;
  `-O` writes magic 0405. The entry point (`-e`) is the symbol's value.
- `-lX` opens `/lib/libX.a`, then `/usr/lib/libX.a` - under the MUTOS
  root (below) -, never the current directory; `-l` alone is `-la`.
- The output is written as `..ldtmp` and six digits in the current
  directory and linked to `a.out` at the end (an old `a.out` is removed
  first); with `-o name` it is written as `name` directly. On success it
  is made executable (0777 less the umask), on errors it is left as
  `creat()` made it (0666 less the umask). `/tmp/ldaXXXXXX` holds the
  data and the local symbols on the way (created and unlinked at once).
- Messages go to stdout, as `ld:file(member): text`; the exit status is 0,
  1 (undefined symbols, multiply defined, an overflow, "No relocation
  bits", "Entry point not in text" - the output is written) or 4 (a fatal
  error: "cannot open", "Bad format", "Premature EOF", ... - no output,
  but with `-o` the file created so far stays).
- `-r` and `-d`: "ld: -r and -d flags not supported", exit status 4 - in
  the original. `mutos_ld`: see "The extension".

## Options and files

`mutos_ld [-o name] [-u sym] [-e sym] [-D size] [-v name] [-lX] [-x] [-X]
[-S] [-s] [-i] [-n] [-O] [-t] [-r] [-d] file ...`, letter by letter as
the original reads them (`-xs`), an option's argument the next word.

Paths: what the original has compiled in as an absolute path of the MUTOS
file system - `/lib/libX.a`, `/usr/lib/libX.a`, `/tmp/ldaXXXXXX` - is
looked up under the MUTOS root (`$MUTOS_ROOT`, by default the build tree's
`mutos_root/`; `src/h/mutos_root.h`); a name from the command line (an
input, `-o`) is the host's, relative to the current directory as on
MUTOS. So the root needs `lib/`, `usr/lib/` and `tmp/` (`make` makes
them). The output is linked to `a.out` with a hard link, as on MUTOS; on
a host file system without hard links (FAT, some network shares) the port
renames it instead, which leaves the same `a.out`.

## The extension: `-r` and `-d`

The original refuses them; `mutos_ld` keeps them (`docs/TOOLCHAIN_PLAN.md`,
decision 5) with v7's meaning: `-r` writes a relocatable object - the
relocation words kept (bit 15 included: the original still computes them
in `load2td()`), the commons left undefined, no "Undefined:" list (the
exit status is 1 all the same if anything is undefined, as v7's), `-i`,
`-n` and `-O` ignored, `-s` taken as `-x`; `-d` defines the commons even with `-r` - and
also `_etext`, `_edata` and `_end`, as v7's, so that a second link of a
program that uses them says "Multiply defined". Its data and BSS values
follow MUTOS's object convention (offsets in their own segment), and a
pc-relative reference to an undefined symbol stays relative to the
object. Every place is marked "EXTENSION" in `ld.c`; without `-r` and `-d`
none of it runs. There is no original to compare with; checked by
`tests/mutos_ld/check_rflag.py`.

## Source layout

- `ld.h` - the memory image, the original's data addresses, the strings.
- `ld.c` - `ld.o`'s functions in the binary's order, `delexit()` to
  `flush()`, `bytrel()` after `load2td()`; the extension marked.
- `ldlib.c` - the machine: the image's initial state (crt0's argument
  words), the system calls on the host's files, libc.a's printf (stdout
  in 512-byte blocks), `atoi()`, `mktemp()`, `strncmp()`, `exit()`, the
  signals, the refusals.
- `lddata.c` - generated: the binary's initialized data.
- `main.c` - the entry.
